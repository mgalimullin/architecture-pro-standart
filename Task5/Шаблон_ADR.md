### <a name="_3bfxc9a45514"></a>**Функциональные требования**
Опишите здесь верхнеуровневые Use Cases. Их нужно оформить в виде таблицы с пошаговым описанием:

|**№**|**Действующие лица или системы**|**Use Case**                   |**Описание**                          |
| :-: | :- | :- | :- |
| **F1** | Клиент (через интернет-банк) | Подача кредитной заявки | Авторизованный клиент заходит в интернет-банк, выбирает тип кредита, сумму, срок и отправляет заявку. |
| **F2** | Клиент (через сайт) | Подача кредитной заявки | Новый клиент заполняет веб-форму на сайте, оставляет контактные данные и параметры кредита. |
| **F3** | Credit Application Service (CAS) | Приём и валидация заявки | CAS принимает заявку от канала (сайт/ИБ), валидирует данные и сохраняет в БД. |
| **F4** | CAS → Кредитный конвейер (Camunda) | Передача заявки на обработку | После валидации CAS ставит заявку в очередь и передаёт в Camunda для запуска бизнес-процесса. |
| **F5** | Кредитный конвейер → Скоринг-сервис | Запрос скоринга | Конвейер вызывает скоринг-сервис для оценки кредитного риска. |
| **F6** | Скоринг-сервис → Бюро КИ | Запрос кредитной истории | Скоринг обращается к внешним API бюро кредитных историй и получает отчёт. |
| **F7** | Конвейер → АБС | Создание кредитного продукта | После одобрения заявки данные о кредите передаются в АБС для учёта. |
| **F8** | CAS → SMS-шлюз | Уведомление клиента | После завершения процесса CAS отправляет клиенту SMS с результатом заявки. |
| **F9** | Интернет-банк | Отображение статуса заявки | Клиент может видеть текущий статус заявки (на рассмотрении, одобрена, отклонена). |


### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
Опишите здесь нефункциональные требования и архитектурно значимые требования.

|**№**|**Требование**|
| :-: | :-           |
| **R1** | Время отклика CAS на приём заявки — не более 1 секунды |
| **R2** | Доступность CAS — 99.9% |
| **R3** | Асинхронная интеграция с конвейером через очередь (Kafka / RabbitMQ) |
| **R4** | Безопасность: HTTPS, JWT, шифрование персональных данных |
| **R5** | Масштабируемость CAS — горизонтальная (контейнеризация, балансировщик) |
| **R6** | Надёжность — гарантированная доставка сообщений (очереди с подтверждением) |
| **R7** | Трассировка заявок и логирование всех статусов |
| **R8** | Совместимость — REST API, JSON, поддержка Oracle (АБС) и MS SQL (ИБ) |
| **R9** | Новые клиенты идентифицируются офлайн (регуляторное ограничение) |
| **R10** | SLA: время обработки заявки не более 5 минут в среднем |

### <a name="_qmphm5d6rvi3"></a>**Решение**
[диаграмы](diagram.png)
[диаграмы 2](diagram2.png)

- Для выполнения F1–F3 выбран CAS как центральный шлюз заявок.
- Асинхронное взаимодействие через очередь реализует R3, R6, защищает Camunda от перегрузки.
- CAS разделён на API и Worker для соблюдения SLA (R1, R10) и масштабируемости (R5).
- Безопасность: HTTPS, JWT, шифрование (R4).
- Все интеграции REST/JSON (R8).
- Логирование и трассировка — для мониторинга процесса (R7).
- Конвейер Camunda оркестрирует бизнес-процесс, скоринг и взаимодействие с АБС (F4–F7).


### <a name="_bjrr7veeh80c"></a>**Альтернативы**
| Вариант | Описание                                             | Недостатки                                                                 |
| :------ | :--------------------------------------------------- | :------------------------------------------------------------------------- |
| 1       | Отправка заявок напрямую в Camunda из интернет-банка | Риск перегрузки Camunda, отсутствие буферизации, сложность масштабирования |
| 2       | Использование ESB как посредника                     | Избыточно для MVP, потребует настройки маршрутов и поддержки               |
| 3       | Синхронное взаимодействие без очереди                | Потеря надёжности, возможные таймауты и дублирование                       |


**Недостатки, ограничения, риски**
- CAS — новый сервис, требует поддержки DevOps и мониторинга.
- Kafka должна быть надёжно сконфигурирована (репликация, ретраи).
- Возможны задержки в передаче статусов (R6, R10).
- Регуляторные ограничения при работе с новыми клиентами (R9).
- Скоринг зависит от внешних систем (R8).
- Необходимость SLA и системной трассировки для инцидентов (R7, R10).
