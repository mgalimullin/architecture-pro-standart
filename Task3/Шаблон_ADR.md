### <a name="_3bfxc9a45514"></a>**Функциональные требования**
Опишите здесь верхнеуровневые Use Cases. Их нужно оформить в виде таблицы с пошаговым описанием:

|№|Действующие лица / системы|Use Case|Описание|
|:-:|---|---|---|
|1|Клиент, Сайт|Подача заявки с сайта|Клиент оставляет Ф.И.О. и телефон → заявка поступает в систему кол-центра (внутренний CC) → менеджер звонит и договаривается об оффлайн-идентификации.|

|3|Back-office (депозиты)|Обработка заявки в MVP|Менеджер бэк-офиса просматривает заявку в АБС (или в интерфейсе админки), устанавливает ставку (из Rates Service), подтверждает — АБС создаёт депозит. Клиент получает SMS.|
|4|Кол-центр|Консультации по ставкам|Операторы видят актуальные ставки — через API Rates Service или выгрузку; партнёрский кол-центр получает файлы CSV.|
|5|DevOps/Monitoring|Наблюдение|Операции и метрики попадают в мониторинг; алерты при снижении SLA.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Интеграция интернет-банка напрямую с АБС (синхронно) — быстро, но риск перегрузить АБС; противоречит требованию избыточности.
2. Использовать таблицы Excel на общем шаре — оставляет человеческий фактор, не масштабируется.
3. Использовать коммерческую rate-engine (SaaS) — быстро, но сложности с интеграцией и требования к безопасности/регуляторике.

**Недостатки, ограничения, риски**
- Появление новых сервисов требует поддержки (SRE/DevOps).
- Необходимы ETL/адаптеры для корректного создания заявок в АБС; возможны несоответствия данных.
- Регуляторное требование по личной идентификации — нельзя автоматизировать полностью.
- Формат CSV для партнёра — задержка свежести данных (например, delta 1–4 часа)
